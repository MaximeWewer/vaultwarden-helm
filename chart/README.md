# Vaultwarden Helm

Helm chart for [Vaultwarden](https://github.com/dani-garcia/vaultwarden), the Bitwarden-compatible server, built for production: multi-replica, operator-managed PostgreSQL with PITR, backups on by default, hardened pods.

## Architecture

| Component | Type | Role |
|-----------|------|------|
| `server` | Deployment | Vaultwarden (Rocket on `:8080`, unprivileged, read-only root FS). `replicas: 3` by default. `RollingUpdate` (maxUnavailable 0) on shared storage, `Recreate` on RWO/sqlite |
| `scheduler` | Deployment | Same image and config, **1 pod, no traffic** (not selected by the Service). Rendered when several server pods can run: the only pod running the scheduled jobs, the server pods get `JOB_POLL_INTERVAL_MS=0` |
| `db` | CNPG `Cluster` | PostgreSQL via **[CloudNativePG](https://cloudnative-pg.io)**: 3 instances (1 primary + 2 streaming replicas, automated failover), anti-affinity, operator PDBs. App credentials generated by the operator in `<release>-vaultwarden-db-app` (`uri` → `DATABASE_URL`) |
| `db-backup` | `ObjectStore` + `ScheduledBackup` | **[barman-cloud plugin](https://github.com/cloudnative-pg/plugin-barman-cloud)**: continuous WAL archiving + scheduled base backups → point-in-time recovery |
| `backup` | CronJob | **restic** snapshots of the files (attachments, sends, icon cache): encrypted, deduplicated, retention + `restic check` |
| `bucket` | Job | Creates the S3 bucket (rclone, idempotent), S3 mode with RustFS or `storage.s3.createBucket` |
| `rustfs` | sub-chart (optional) | **[RustFS](https://github.com/rustfs/rustfs)** S3-compatible object store when you have no S3 |

## Storage modes (`storage.mode`)

Vaultwarden keeps attachments, Sends and the icon cache on a filesystem or object store. Pick the first one your infrastructure supports:

| Mode | Replicas | Requirement | Notes |
|------|----------|-------------|-------|
| `rwx` (default) | N | A **ReadWriteMany** StorageClass (NFS, CephFS, Longhorn RWX, EFS…) | One PVC shared by every pod. Official image |
| `s3` + external S3 | N | An S3 bucket **reachable by end users** | Uses `image.s3Repository` (see below). Allow your vault origin in the bucket **CORS** for the web vault |
| `s3` + `rustfs.enabled` | N | Nothing (RustFS deployed by the chart) | RustFS served **same-origin** on `https://<domain>/<bucket>/` through the chart Ingress/HTTPRoute: no CORS, SigV4 stays valid (Host preserved) |
| `rwo` | **1** | Any StorageClass | Fallback. `Recreate` strategy. `replicas > 1` is rejected at render time |

### RWX without a RWX StorageClass (static PV)

A filesystem already mounted on every node (CephFS, NFS, GlusterFS...) but no dynamic RWX StorageClass: declare a static `PersistentVolume` + `PersistentVolumeClaim` once, then point the chart at it with `storage.persistence.existingClaim` (the chart then creates no PVC):

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: vaultwarden-data
spec:
  capacity: { storage: 5Gi }
  accessModes: [ReadWriteMany]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""            # static binding, no provisioner
  claimRef: { namespace: vaultwarden, name: vaultwarden-data }
  # Option A: the shared mount is present at the same path on every node
  hostPath:
    path: /mnt/cephfs/vaultwarden
    type: DirectoryOrCreate
  # Option B (preferred): let kubelet mount it, no node-side setup
  # nfs: { server: nfs.example.com, path: /exports/vaultwarden }
  # cephfs / csi: see your driver's static provisioning docs
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: vaultwarden-data
  namespace: vaultwarden
spec:
  accessModes: [ReadWriteMany]
  storageClassName: ""
  volumeName: vaultwarden-data
  resources: { requests: { storage: 5Gi } }
```

```yaml
storage:
  mode: rwx
  persistence:
    existingClaim: vaultwarden-data
```

With `hostPath`, Kubernetes does not check that the path is really shared: if a node lacks the mount, its pod silently writes to the local disk and attachments diverge between pods. Make the directory writable by the pod uid/gid (`1000:1000` by default; `fsGroup` is **not** applied to hostPath volumes). The restic backup works unchanged (the CronJob mounts the same claim).

**Why the S3 endpoint must be public.** With an object store, Vaultwarden does not stream attachments itself: it returns a **presigned URL** on the S3 endpoint and the client (browser, mobile, desktop) downloads from there. An in-cluster Service URL would break attachments and Sends for every user. With RustFS the chart therefore defaults the endpoint to your vault origin and adds a `/<bucket>/` route to RustFS (bucket names colliding with Vaultwarden routes (`api`, `admin`, `attachments`…) are rejected). Pods reach S3 through that same public URL (hairpin through the ingress); the chart Jobs use the in-cluster Service.

**Images (Alpine).** The chart runs the **Alpine** variant: `image.tag` empty → `<appVersion>-alpine` (set `image.tag` explicitly for another variant, e.g. `1.37.5` for Debian). The official image is built **without** the `s3` cargo feature, so in `s3` mode the chart switches to `image.s3Repository` (`ghcr.io/maximewewer/vaultwarden-s3`), built by this repository's `build-image` workflow from the **unmodified upstream sources and `docker/Dockerfile.alpine`** with `DB=sqlite,mysql,postgresql,enable_mimalloc,s3` (upstream Alpine defaults + `s3`). The workflow always builds `chart/Chart.yaml` `appVersion` and tags `<appVersion>-alpine`, so chart and image stay in lockstep.

## High availability

Vaultwarden is a single-process design; running several replicas works with a shared DB and data store, with these caveats (all handled or documented by the chart):

| Concern | Handling |
|---------|----------|
| JWT signing key (`rsa_key.pem`) must be identical on every pod | Generated once into the chart Secret (`rsa-private-key`), mounted read-only. **Validated**: a token issued by one pod is accepted by the others |
| Live-sync WebSocket notifications are in-memory per pod | Cookie stickiness on the ingress / gateway (examples under `ingress.annotations`). Service `sessionAffinity` is off by default: controllers route to the pod endpoints and ignore it, and a proxy going through the Service would pin all its traffic to one pod. Enable `config.push` (Bitwarden relay) for mobile push (pod-independent) |
| Rate limits (login/admin) are per pod | Effective limit = limit × replicas |
| Admin-panel settings (`config.json`) are read at pod start only | Drive configuration through values/env. `storage.s3.configFileInBucket: true` shares the file in S3 (then roll the Deployment after an admin change) |
| Scheduled jobs run in every Vaultwarden process, and some send mails (incomplete 2FA login, emergency-access reminders / timeouts): N replicas = N mails | Dedicated `scheduler` Deployment (1 pod, no traffic) runs them; server pods get `JOB_POLL_INTERVAL_MS=0`. `scheduler.enabled: false` to opt out |
| DB connections | `config.databaseMaxConns` is **per pod**: keep `replicas × databaseMaxConns` below PostgreSQL `max_connections` |
| Startup ordering | `DB_CONNECTION_RETRIES=0` (wait forever for the DB, bounded by the startupProbe); S3 mode adds a `wait-for-s3` init container |
| Disruptions | PDB (`maxUnavailable: 1`), topology spread across nodes/zones, optional HPA |

Probes: readiness on `/alive` (also checks the DB, so a pod losing the DB leaves the Service); liveness is a TCP check, so a DB outage does not restart every pod.

## Prerequisites

- Kubernetes 1.29+, Helm 3.8+ (OCI).
- `database.type: cnpg` (default): the **CloudNativePG operator**, and for database backups the **barman-cloud plugin** (requires cert-manager):
  ```sh
  helm repo add cnpg https://cloudnative-pg.github.io/charts
  helm install cnpg cnpg/cloudnative-pg -n cnpg-system --create-namespace
  kubectl apply -f https://github.com/cloudnative-pg/plugin-barman-cloud/releases/download/v0.15.1/manifest.yaml
  ```
- An **off-site S3 bucket** for backups (or explicitly disable them, see below).
- `rustfs.enabled`: `helm dependency build .` before installing from source.

## Install

```sh
helm install vaultwarden oci://ghcr.io/maximewewer/charts/vaultwarden \
  --version 1.37.5-05-11-2026 \
  -n vaultwarden --create-namespace \
  --set config.domain=https://vault.example.com \
  --set ingress.enabled=true --set ingress.className=nginx --set ingress.host=vault.example.com \
  --set backup.s3.endpoint=https://s3.backup.example.com \
  --set backup.s3.bucket=vaultwarden-backups \
  --set backup.s3.existingSecret=vaultwarden-backup-s3
```

Chart versions are `<vaultwarden version>-<DD-MM-YYYY>`, which semver reads as a pre-release: Helm only resolves them with an explicit `--version` (recommended, pin it), or `--devel` for the latest one.

The chart **fails at render time** on unsafe combinations instead of deploying something broken: missing `config.domain`, `replicas > 1` with `rwo` or `sqlite`, S3 mode without credentials, backups enabled without a target, RustFS without S3 mode, colliding bucket names…

### Secrets

When `config.existingSecret` is empty the chart generates `<release>-vaultwarden-secret` (kept on uninstall). Per-key resolution: inline `config.secrets.*` > existing in-cluster Secret (`lookup`) > generated (`rsa-private-key`, `admin-token`).

| Key | Used for |
|-----|----------|
| `rsa-private-key` | JWT signing key, **required** (shared by all pods). `openssl genrsa 2048` |
| `admin-token` | `/admin` when `config.admin.enabled` (prefer an Argon2 PHC string) |
| `smtp-password` | SMTP auth when `config.smtp.username` is set |
| `push-installation-key` | Bitwarden push relay (`config.push`) |
| `sso-client-secret` | OpenID Connect (`config.sso`) |
| `database-url` | `database.type: external` with an inline `externalDatabase.url` |

**ArgoCD without a secret manager:** set `config.secrets.rsaPrivateKey` (and `adminToken`) inline or use `config.existingSecret`. Argo's `lookup` is unreliable during diff/sync: an unset key re-rolls each sync, which logs every user out (new RSA key).

## Backups

Both backups are **enabled by default** and share one S3 target (`backup.s3`). Rendering fails until it is configured, or until you opt out explicitly, e.g. `backup.files.enabled=false` when Velero snapshots the PVC. Use an **off-site** bucket, not the bundled RustFS.

| What | How | Default schedule | Retention |
|------|-----|------------------|-----------|
| PostgreSQL | barman-cloud plugin: WAL archiving (continuous) + base backup, `s3://<bucket>/cnpg/<cluster>/` | `0 0 2 * * *` | `30d` recovery window |
| Files | restic, `s3:<endpoint>/<bucket>/restic`. `rwx`/`rwo`: PVC mounted read-only (`rwo`: pod pinned to the vaultwarden node). `s3`: rclone copies the bucket to a scratch volume first. `sqlite`: a consistent copy of the live DB (`vaultwarden backup`, i.e. `VACUUM INTO`) is taken first and backed up instead of the live file; the restore Job puts it back | `30 2 * * *` | 7 daily / 4 weekly / 6 monthly + `restic check --read-data-subset 5%` |
| JWT key | Not in the backups: keep the chart Secret (or your `existingSecret`) in your secret store | n/a | n/a |

The restic repository password is generated once into `<release>-vaultwarden-restic` (kept on uninstall). **Save it off-cluster**: without it the repository cannot be decrypted.

```sh
# Run a file backup now
kubectl create job -n vaultwarden --from=cronjob/vaultwarden-backup vaultwarden-backup-manual
# List DB backups
kubectl get backups.postgresql.cnpg.io -n vaultwarden
```

### Restore: database (disaster recovery / PITR)

Re-install with a recovery bootstrap; the operator restores the last base backup and replays the WALs (optionally up to `targetTime`). Archive the new cluster under a **new** `serverName` (the plugin refuses a non-empty WAL archive):

```yaml
config:
  existingSecret: vaultwarden-restored   # same rsa-private-key as before = users stay logged in
cnpg:
  recovery:
    enabled: true
    objectStore: vaultwarden-db-backup   # ObjectStore holding the backups
    serverName: vaultwarden-db           # source cluster name in the store
    targetTime: ""                       # e.g. "2026-11-05T08:00:00Z" for PITR
backup:
  database:
    serverName: vaultwarden-db-r1        # new archive location
```

### Restore: files

```sh
# 1. Restore mode: the chart scales vaultwarden (server + scheduler) to 0 and runs the
#    restore Job, which waits until vaultwarden no longer answers before writing.
helm upgrade vaultwarden ... --reuse-values --set backup.files.restore.enabled=true \
  --set backup.files.restore.snapshot=latest     # or a restic snapshot id
kubectl wait --for=condition=complete job -l app.kubernetes.io/component=restore -n vaultwarden
# 2. Back to normal: vaultwarden restarts on the restored data.
helm upgrade vaultwarden ... --reuse-values --set backup.files.restore.enabled=false
```

Do not scale the Deployment by hand instead: a `helm upgrade` re-applies `replicas` and would restart vaultwarden while the Job overwrites its data. The Job restores into the data PVC (sqlite: the consistent DB copy taken at backup time), or back into the bucket in `s3` mode. Its name hashes its spec, so changing the snapshot re-runs the restore.

## Extending the chart

| Value | Use |
|-------|-----|
| `commonLabels` / `commonAnnotations` | Added to every resource the chart renders (labels also on the vaultwarden pods, never in selectors). Annotations merge with per-resource ones (`ingress.annotations`, `service.annotations`...) |
| `extraVolumes` / `extraVolumeMounts` | Extra volumes on the vaultwarden container (corporate CA bundle, custom templates...) |
| `extraInitContainers` | Init containers, after the chart's own `wait-for-s3` |
| `sidecars` | Sidecar containers (log shipper, proxy...). Give them a hardened `securityContext` |
| `extraObjects` | Any extra manifest released with the chart (ExternalSecret, NetworkPolicy, ConfigMap...) |
| `dnsPolicy` / `dnsConfig` | Pod DNS settings (e.g. `ndots`) |
| `probes.startup` / `readiness` / `liveness` | Full probe objects. Overrides are merged with the defaults: null the old handler to switch (`tcpSocket: null`), or set a probe to `null` to drop it |

`extraVolumes`, `extraVolumeMounts`, `extraInitContainers`, `sidecars` and `extraObjects` go through `tpl`: entries may be YAML or strings and may use `{{ include "vaultwarden.fullname" . }}`, `{{ .Release.Namespace }}`...

Corporate CA example (icons, SSO IdP, SMTP or S3 behind an internal PKI):

```yaml
extraVolumes:
  - name: corp-ca
    configMap:
      name: corp-ca-bundle
extraVolumeMounts:
  - name: corp-ca
    mountPath: /etc/ssl/certs/corp-ca.crt
    subPath: ca.crt
    readOnly: true
config:
  extraEnv:
    - name: SSL_CERT_FILE
      value: /etc/ssl/certs/corp-ca.crt
```

`SSL_CERT_FILE` replaces the system bundle: put the public roots in the same file if Vaultwarden must also reach public hosts (push relay, icons).

ExternalSecret example (secrets from Vault / a cloud secret manager, then `config.existingSecret: vaultwarden-secret`):

```yaml
extraObjects:
  - apiVersion: external-secrets.io/v1
    kind: ExternalSecret
    metadata:
      name: vaultwarden-secret
    spec:
      secretStoreRef: { kind: ClusterSecretStore, name: vault }
      target: { name: vaultwarden-secret }
      dataFrom:
        - extract: { key: secret/vaultwarden }
```

## Security

- Pods run as uid `1000`, `runAsNonRoot`, `readOnlyRootFilesystem`, `drop: [ALL]`, `seccompProfile: RuntimeDefault`, no ServiceAccount token, no service links. Same for every Job/CronJob.
- NetworkPolicy (on by default, server + scheduler pods): ingress on the web port only (`networkPolicy.allowedFrom`). Egress derived from the configuration: DNS, in-namespace CNPG (5432) / RustFS (9000) when used, the external DB port (`externalDatabase.port`, restrict with `externalDatabase.networkPolicyPeers`) and the S3 endpoint port (incl. the vault origin when RustFS is routed through the ingress), both towards external IPs **and every in-cluster pod** (in-cluster DB, ingress hairpin; Cilium does not match pod IPs with `ipBlock`); the SMTP port and HTTPS out for icons / push relay / SSO (`networkPolicy.allowInternetHttps`) towards **external IPs only**; plus `networkPolicy.extraEgress`. Note: in `s3` mode with an https endpoint, port 443 stays open through the S3 rule even with `allowInternetHttps: false`.
- Config changes roll the pods (env is in the pod spec; inline `config.secrets.*` via a `checksum/inline-secrets` annotation). Changes to `config.existingSecret` or other referenced Secrets are not tracked: use [Reloader](https://github.com/stakater/Reloader) (`podAnnotations: { reloader.stakater.com/auto: "true" }`).
- `/admin` disabled unless `config.admin.enabled`; sign-ups closed by default.
- `rsa-private-key`, restic password and RustFS credentials Secrets carry `helm.sh/resource-policy: keep`.

## Metrics

Vaultwarden exposes no Prometheus endpoint. `metrics.enabled` + `metrics.podMonitor.enabled` create a `PodMonitor` for the CNPG instances (built-in exporter on `:9187`). RustFS exports OTLP (`rustfs.config.rustfs.obs_endpoint`).
